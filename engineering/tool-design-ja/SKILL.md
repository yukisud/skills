# ツール設計スキル(要件定義〜仕様書)

業務ツール開発の上流を担当する。**設計と実装を分離**し、このスキルの成果物(仕様書)を `engineering/tool-development-ja` に引き継ぐ。既存ツールの改修は `engineering/tool-maintenance-ja` が担当。

## Phase 1: 要件定義

### 1-1. 問題の言語化(ツールの話をする前に)
- 誰が・どの業務で・何に時間を使っている/何を間違えているか。**頻度×時間×人数で現状コストを数値化**する(月2時間の作業に40時間の開発をしない)
- 成功条件を1文で(「検索語句レポートの処理が週60分→10分になる」)

### 1-2. 作らない選択肢の検討(必須)
| 代替 | 検討事項 |
|---|---|
| 既製SaaS | 月額と開発・保守コストの比較。カスタマイズ欲求が本当に必須か |
| スプレッドシート+関数 | 関係者が自力で直せる最強の保守性 |
| 既存ツールの設定変更 | Looker Studio・GAS・Zapier/Make等の組み合わせで足りないか |
| 手順の改善 | ツール不要で業務手順の変更だけで解決しないか |

作る判断をした場合、**なぜ代替では駄目か**を仕様書に1行残す(将来の「なんでこれ自作したんだっけ」を防ぐ)。

### 1-3. スコープ定義
- MVP(最初のリリース)に入れる機能を**3つ以内**に絞り、それ以外は「次期以降リスト」へ明示的に送る
- 非機能要件を確認: データ量(件数・増加率)/ 利用者数と権限 / 扱うデータの機微度(個人情報・クライアントデータの有無)/ 求める可用性(止まったら業務が止まるか、翌日でいいか)

## Phase 2: 技術選定

### 選定原則
1. **保守できる人がいる技術 > 最適な技術**。作った人しか触れないツールは負債
2. 退屈な技術(枯れた定番)を優先。新技術の検証はツール開発に混ぜない
3. 段階を飛ばさない: スクリプト→定期実行→Webアプリ の順で、必要になってから昇格する

### 業務ツールの定番構成(日本の中小規模チーム)
| 規模・用途 | 推奨 | 理由 |
|---|---|---|
| データ処理・レポート生成(手動実行) | Pythonスクリプト or GAS | 最小。GASはスプレッドシート直結・認証不要が強い |
| 定期実行(監視・自動レポート) | GAS(トリガー) / GitHub Actions(cron) / Cloud Run Jobs | GASは6分/回の実行制限に注意 |
| 社内向けWeb UI | スプレッドシート+GAS Webアプリ / Streamlit / Next.js | 「UIが本当に必要か」を先に疑う |
| クライアントも使う外部公開 | Next.js/Rails等+マネージドホスティング | 認証・セキュリティ要件が一段上がる(security-review-ja必須) |
| API連携ハブ | Zapier/Make → 複雑化したらコード化 | ノーコードの分岐が5個を超えたらコードの方が保守しやすい |

## Phase 3: デプロイ先選定

| デプロイ先 | 向き | 判断ポイント |
|---|---|---|
| GAS | Google Workspace内で完結する処理 | 無料・認証込み。実行時間制限、Git管理しにくい(claspで緩和) |
| GitHub Actions | 定期バッチ・リポジトリ連動 | 無料枠内なら運用ゼロ。シークレット管理はActions Secrets |
| Cloud Run / Cloud Functions | API・バッチ全般 | 従量課金でアイドル無料。**リージョンはasia-northeast1(東京)**を既定に |
| Vercel / Netlify | フロントエンド・軽いAPI | プレビュー環境が自動。商用プランの条件確認 |
| VPS・レンタルサーバー | WordPress同居・常駐処理 | 自前運用の保守コストを見込む。既にXserver等を契約済みなら同居も合理的 |

- **個人情報・クライアントデータを扱う場合**: 保存先の所在(国内リージョン)、アクセス権、ログの扱いを仕様書に明記(越境移転の整理は `engineering/security-review-ja` §10)
- 判断基準の優先順: 運用の手間 > 費用 > 性能。月数百円をケチって毎月の手動運用を残さない

## Phase 4: 仕様書(このスキルの納品物)

```
# ツール仕様書: (名前) vX.X
## 目的と成功条件(1-1の結果。現状コストと目標)
## 作る判断の根拠(1-2。代替案とその棄却理由)
## スコープ(MVP機能3つ以内 / 次期以降リスト)
## 利用者と権限(誰が・何を・どこまで)
## データ設計(入力元/形式/保存先/保持期間。個人情報の有無と扱い)
## 処理フロー(入力→処理→出力をステップで。エラー時の挙動込み)
## 画面・出力仕様(UIがある場合はワイヤー、レポートなら出力サンプル)
## 技術構成とデプロイ先(Phase 2-3の結論と理由)
## 非機能(実行頻度・想定データ量・失敗時の通知先・監視方法)
## セキュリティ要件(認証、シークレット管理、security-review-jaのチェック対象§)
## 受け入れ条件(この操作をしてこうなったら完成、を具体的に列挙)
```

## 原則

- ユーザーへの確認は Phase 1 でまとめて行う(実装が始まってからの要件変更が最も高くつく)。不明点を推定で埋めた場合は仕様書に「仮定」と明記する。
- 受け入れ条件のない仕様書を実装に渡さない(「完成」の定義がないと開発が終わらない)。
- 過剰設計の抑制: MVPにログイン機能・管理画面・設定画面が本当に必要か毎回疑う。利用者3人のツールに汎用性はいらない。
