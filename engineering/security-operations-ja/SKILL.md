# 防御セキュリティ運用スキル

**防御(ブルーチーム)専用。** 検知・対応・復旧・再発防止を扱い、攻撃コード・侵入手順・検出回避は作らない。コード変更前の監査は `engineering/security-review-ja`、外部ツール導入監査は `engineering/skill-vetting`、原因調査の型は `engineering/systematic-debugging-ja`。

> 元ネタ: mukul975/Anthropic-Cybersecurity-Skills(MITRE ATT&CK/NIST CSF準拠)の**防御ドメインのみ**を日本の中小規模運用向けに再構成。攻撃・dual-use領域は意図的に除外。専門的な対応が必要な重大インシデントは、判断を抱え込まず外部の専門家(セキュリティベンダー・IPA・JPCERT/CC)へエスカレーションする前提。

## 0. 最初の判断(通報か対応か)

- **人命・重大な情報漏えい・金銭被害が進行中**なら、調査より先に止血と通報。個人データ漏えいは個人情報保護委員会への報告義務(`security-review-ja` §10)。ランサムウェア・不正送金は警察・JPCERT/CCへ
- 自分の権限・力量を超えるインシデントは、握りつぶさずエスカレーション先を明示して引き継ぐ(「様子見」で時間を溶かさない)

## 1. インシデント対応(NISTの6フェーズ)

| フェーズ | やること | 注意 |
|---|---|---|
| 準備 | 連絡網・権限・ログ保全先を平時に用意 | インシデント時に作り始めると間に合わない |
| 検知・分析 | 何が・いつ・どの範囲で起きたかを事実で把握 | 推測と事実を分ける(`systematic-debugging-ja`) |
| 封じ込め | 影響拡大を止める(隔離・アカウント無効化・通信遮断) | **証拠を保全してから**。復旧を急いで痕跡を消さない |
| 根絶 | 原因(不正アカウント・脆弱性・マルウェア)を除去 | 入口を塞がずに復旧すると再侵入される |
| 復旧 | クリーンな状態から段階復旧+監視強化 | いきなり全開放しない |
| 教訓 | ポストモーテム(犯人探しでなく仕組み改善) | `systematic-debugging-ja` のポストモーテム原則 |

- タイムラインを1本作る(いつ何が起きたか・誰が何をしたか)。対応操作もすべて記録する
- 封じ込めの副作用(サービス停止)は事業判断。独断で全停止せず、影響と選択肢を意思決定者に上げる

## 2. 脅威ハンティング(仮説駆動)

「アラートを待つ」でなく「侵害されているとしたらどこに痕跡が出るか」を仮説にして探す:
- 典型の観点: 通常と違う時間帯・場所からのログイン/新規に作られた管理者アカウント/見慣れないプロセス・スケジュールタスク/外部への大量送信・不審なドメインへの通信/権限昇格の痕跡
- **ベースラインを先に作る**(平常時が分からないと異常が分からない)。`management/command-logger` のログや各SaaSの監査ログが素材
- 見つけたら §1のインシデント対応へ。見つからなかったことも記録(次回の効率化)

## 3. ログ調査

- 調査の起点を1つ決めてから広げる(全ログを眺めない)。時刻・アカウント・IP・操作のいずれかを軸に相関を取る
- タイムゾーンを最初に統一(`data-reconciliation` と同じ罠。UTC/JST混在で時系列が壊れる)
- **改ざん・削除の可能性を前提に**、原本を保全してからコピーで作業する
- 外部送信・権限変更・削除系・認証失敗の連続、の4パターンを定点観測(`command-logger` の週次レビュー観点と同じ)

## 4. 脆弱性トリアージ

検出された脆弱性(`security-review-ja` §7の依存監査、外部スキャン結果等)を、全部同時に直せない前提で優先順位付け:
- **深刻度 × 悪用可能性 × 資産の重要度**で並べる。CVSSスコアだけで判断しない(公開資産のCriticalと、内部限定のHighでは前者が先)
- 既知の悪用が出回っている(KEV相当)ものは深刻度に関わらず最優先
- すぐ直せないものは緩和策(アクセス制限・監視強化・機能停止)を記録し、恒久対応の期限を決める

## 出力様式

```
## セキュリティ対応: (事象)(日時)
### 状況(事実。確認済み/未確認を区別)
### 影響範囲と緊急度
### 実施した対応(タイムライン)
### 通報・エスカレーション要否(義務のある報告先を明示)
### 次のアクション(封じ込め/根絶/復旧のどこにいるか)
### 再発防止(恒久対応と期限)
```

## 原則

- 攻撃の実行・攻撃コードの作成・検出回避の支援はしない(このスキルは防御専用)。正当なペネトレーションテストが必要なら、書面許可のある専門業者に依頼する範囲まで
- 確認できていないことを断定しない。インシデント報告での憶測は二次被害を生む
- 対応記録は監査可能な形で残す(`command-logger` のログと突合できるように)
