# ツール開発実働スキル

仕様書(`engineering/tool-design-ja` の成果物)を受け取り、動くツールとして納品する。仕様書がない場合は最低限「目的・入出力・受け入れ条件」を確認してから着手する(口頭要件のまま書き始めない)。

## 開発の進め方

### 1. 着手前
- 仕様書の受け入れ条件を読み、**最初にテスト・検証方法を決める**(何をもって完成とするか)
- リポジトリ・ブランチを用意(既存リポジトリなら作業ブランチ、新規なら初期化+.gitignore)。GASも clasp でGit管理に乗せる
- シークレット(APIキー等)は最初から環境変数/Secretsで扱う。「あとで直す」つもりのハードコードをしない

### 2. 実装
- **縦に切って小さく出す**: 機能Aを入力→処理→出力まで貫通させてから機能Bへ。全機能を横に半分ずつ作らない(いつまでも動くものがない状態を避ける)
- 動作可能な最小単位ごとにコミット。コミットメッセージは変更理由がわかる日本語で
- エラー処理は仕様書の「エラー時の挙動」に従う。**握りつぶし(空catch)を書かない**。定期実行ツールは失敗時の通知(メール/Slack/LINE)を必須実装とする
- 外部API(Google Ads・SC・GA4等)はレート制限・リトライ(指数バックオフ)・タイムアウトを最初から入れる
- 日本語データの処理は文字コード(UTF-8/Shift_JIS混在のCSV)、全角半角、日付形式(和暦・YYYY/MM/DD)の正規化を早期に共通化する

### 3. テストと検証
- 受け入れ条件を1件ずつ実際に実行して確認する(コードを眺めて「動くはず」で完了にしない)
- データ処理ツールは**実データのコピーで検証**し、期待値を手計算・スプレッドシートで独立に作って突合(`data-science/data-reconciliation` の考え方)
- 境界ケース: 0件データ、巨大データ、日本語・絵文字入りデータ、月末月初・年跨ぎの日付
- 失敗した場合の調査は `engineering/systematic-debugging-ja` のプロセスで

### 4. 出荷前ゲート(スキップ不可)
1. **`engineering/security-review-ja`** を差分スコープで実行(シークレット・入力検証・依存関係は最低限。外部公開・個人情報ありならフル)
2. 受け入れ条件の全件パスを確認し、結果を記録
3. 仕様との差分(実装中に判断で変えたこと)を列挙してユーザーに報告

### 5. デプロイ
- 仕様書のデプロイ先に従う。初回デプロイは動作確認手順とセットで(デプロイして終わりにせず、本番で受け入れ条件の主要1件を再実行)
- ロールバック手段を確認してからデプロイ(直前バージョンへの戻し方を README に書く)
- 定期実行はデプロイ後、**初回の自動実行が成功するまで**見届ける(手動では動くがcron環境で環境変数不足、が定番の事故)

## 納品物(コード以外に必ず付ける)

```
README.md に含めるもの:
- これは何か(1段落)・仕様書へのリンク
- セットアップ手順(ゼロから動かすまで。環境変数一覧と取得方法)
- 使い方(通常運用で叩くコマンド/画面操作)
- 定期実行の仕組みと失敗時の対応(通知はどこに来るか、よくある失敗と対処)
- ロールバック手順
```

- 引き継ぎの基準: **作者以外が README だけで再セットアップできる**こと。属人化したツールは資産でなく負債。
- 運用開始後の実行ログ・監査は `management/command-logger` の方針に準じる。

## 原則

- 仕様にない機能を勝手に足さない(良かれの追加機能が保守対象を増やす)。欲しくなったら「次期以降リスト」へ。
- 実装中に仕様の矛盾・抜けを見つけたら、勝手に解釈せず選択肢と推奨を添えて確認する(自律実行中は推奨案を採用し、判断した旨を報告に残す)。
- 完了報告は `management/agent-team-orchestration-ja` の報告様式(結論/成果物/判断したこと/懸念/未対応)で行う。
