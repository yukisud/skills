# セキュリティレビュースキル(包括版)

自分たちが書いた・変更したコードと設定を対象にした防御目的のレビュー。**検出と修正提案のみを行い、攻撃コード・悪用手順は作らない。** 外部から入手したスキル・ツールの監査は `engineering/skill-vetting`、実行ログでの事後監査は `management/command-logger` が担当。

## 実行タイミングとスコープ

| タイミング | スコープ |
|---|---|
| PR前・機能実装後 | 差分ファイル+その呼び出し経路(§2〜§6を差分に該当する範囲で) |
| リリース前・公開前 | 全章フルチェック |
| 定期(月次) | §1シークレット・§7依存関係・§9インフラ設定 |

レビュー開始時にまず対象を宣言する: 対象リポジトリ/差分、言語・フレームワーク、外部公開面(URL・API・フォーム)、扱うデータの機微度(個人情報・決済の有無)。

## §1 シークレット・認証情報

- [ ] ハードコードされたAPIキー・パスワード・トークンがないか
```bash
grep -rEni "(api[_-]?key|secret|password|passwd|token|credential)\s*[:=]\s*['\"][^'\"]{8,}" --include="*.{js,ts,py,php,rb,go,java,json,yml,yaml,env,sh}" .
grep -rEn "AKIA[0-9A-Z]{16}|AIza[0-9A-Za-z_-]{35}|sk-[a-zA-Z0-9]{20,}|ghp_[0-9A-Za-z]{36}|xox[bp]-" .
```
- [ ] `.env`・鍵ファイル(`.pem`/`.key`/`credentials.json`)がコミットされていないか。`.gitignore` に登録されているか
- [ ] **git履歴に過去のシークレットが残っていないか**(`git log -p | grep` またはgitleaks/trufflehog)。見つかったら履歴からの除去+**キーのローテーション必須**(削除コミットだけでは漏えいは解消しない)
- [ ] クライアントサイド(JSバンドル・HTML)にサーバー用シークレットが混入していないか(`NEXT_PUBLIC_`/`VITE_` プレフィックスの誤用)
- [ ] ログ出力にトークン・パスワード・個人情報が流れていないか

## §2 インジェクション

- [ ] **SQL**: 文字列連結でクエリを組み立てていないか。プレースホルダ/ORM使用か
```bash
grep -rEn "(query|execute|raw)\s*\(.*(\+|%s|\$\{|f\")" --include="*.{py,js,ts,php,rb}" .
```
- [ ] **XSS**: `innerHTML`/`dangerouslySetInnerHTML`/`v-html`/`echo $_GET` 等でユーザー入力を未エスケープ出力していないか。出力先コンテキスト(HTML/属性/JS/URL)ごとのエスケープか
- [ ] **OSコマンド**: `exec`/`system`/`subprocess(shell=True)`/バッククォートにユーザー入力が渡っていないか
- [ ] **パストラバーサル**: ファイルパスにユーザー入力(`../`)が入る箇所。正規化+許可ディレクトリ検証があるか
- [ ] **SSTI**: テンプレート文字列自体をユーザー入力から組み立てていないか
- [ ] **正規表現DoS(ReDoS)**: ユーザー入力に適用する複雑な正規表現のバックトラック爆発

## §3 認証・セッション

- [ ] パスワードは bcrypt/argon2 等の適応型ハッシュか(MD5/SHA-1/SHA-256単体・平文・可逆暗号はNG)
- [ ] ログイン・パスワードリセット・OTPにレート制限/ロックアウトがあるか
- [ ] セッションID: ログイン成功時に再発行しているか(セッション固定対策)。ログアウトでサーバー側無効化されるか
- [ ] Cookie属性: `Secure` / `HttpOnly` / `SameSite=Lax以上` が揃っているか
- [ ] JWT: `alg:none` 拒否、署名検証、有効期限、**失効手段**(ログアウト・権限剥奪時)があるか。JWTをlocalStorageに置いていないか(XSSで窃取可能)
- [ ] パスワードリセットトークン: 推測不能・使い捨て・短命か。ユーザー列挙(存在有無でレスポンス差)がないか

## §4 認可(最頻出の重大欠陥)

- [ ] **IDOR**: `/users/123` 等、IDを差し替えると他人のリソースにアクセスできないか。**全エンドポイントで「認証済みか」でなく「そのリソースの所有者/権限者か」を検証**しているか
- [ ] 権限チェックがフロントエンドのみ(ボタン非表示)になっていないか。API側で再検証しているか
- [ ] 管理者機能: URL秘匿(`/admin` を知らないだけ)を防御としていないか
- [ ] マルチテナント: 全クエリにテナントIDの絞り込みが強制されているか(ORMのグローバルスコープ等)
- [ ] マスアサインメント: リクエストボディの `role`/`is_admin` 等をそのままモデルに流し込んでいないか(許可リスト方式か)

## §5 リクエスト強要・外部通信

- [ ] **CSRF**: 状態変更系(POST/PUT/DELETE)にCSRFトークンまたはSameSite+カスタムヘッダ検証があるか。GETで状態変更していないか
- [ ] **CORS**: `Access-Control-Allow-Origin: *` +認証情報許可の組み合わせ、Originのワイルドカード反射をしていないか
- [ ] **SSRF**: ユーザー入力のURLをサーバーがfetchする箇所(画像取得・Webhook・PDF生成)。プライベートIP帯(169.254.169.254のメタデータ含む)への接続を遮断しているか
- [ ] **オープンリダイレクト**: `?redirect=` 系パラメータの検証(許可リスト方式か)
- [ ] **XXE**: XMLパーサの外部エンティティ解決が無効か
- [ ] 安全でないデシリアライゼーション: `pickle`/`unserialize`/`yaml.load` にユーザー入力を渡していないか

## §6 入力・ファイル・出力

- [ ] ファイルアップロード: 拡張子とMIMEの両検証、実行可能ファイル拒否、保存先を公開ディレクトリ外に、ファイル名のサニタイズ(パス注入)、サイズ上限
- [ ] 全入力のサーバー側バリデーション(型・長さ・範囲)。クライアント検証だけに依存していないか
- [ ] エラーメッセージ: スタックトレース・SQL・内部パスをユーザーに露出していないか(本番はデバッグモードOFF: `DEBUG=False`、`APP_ENV=production`)
- [ ] `postMessage` の `origin` 検証、`window.open` の `rel="noopener"`

## §7 依存関係・サプライチェーン

```bash
npm audit --production / pip-audit / bundler-audit / osv-scanner
```
- [ ] 既知CVEのある依存の更新(Critical/Highは即時、直せない場合は緩和策を記録)
- [ ] lockfileがコミットされているか(バージョン固定)
- [ ] 追加パッケージ名のtyposquatting確認、メンテ停止・乗っ取り歴の確認
- [ ] `postinstall` スクリプトを持つ依存の中身確認
- [ ] CDN読み込みのスクリプトにSRI(integrity属性)があるか

## §8 CI/CD・リポジトリ

- [ ] GitHub Actions: `pull_request_target` + checkout の危険な組み合わせ、フォークPRへのシークレット露出がないか
- [ ] Actionsのバージョンをタグでなく**コミットSHAで固定**しているか(サードパーティ製は特に)
- [ ] リポジトリの公開範囲、ブランチ保護、force push制限
- [ ] デプロイ用トークンの権限が最小か(書き込み範囲・有効期限)

## §9 インフラ・設定・Webサイト

- [ ] セキュリティヘッダ: `Content-Security-Policy` / `Strict-Transport-Security` / `X-Content-Type-Options: nosniff` / `X-Frame-Options`(または frame-ancestors)/ `Referrer-Policy`
- [ ] TLS: 全ページHTTPS、HTTP→HTTPSリダイレクト、証明書の自動更新
- [ ] ストレージ(S3/GCS)のバケット公開設定、署名付きURLの有効期限
- [ ] 管理画面・ステージング環境の露出(Basic認証・IP制限・robots対象外)
- [ ] **WordPress等CMS(日本のLP・サイト運用で頻出)**: 本体・プラグイン・テーマの更新、未使用プラグイン削除、`wp-admin` へのアクセス制限、ユーザー名列挙(`?author=1`)対策、DBプレフィックス、バックアップの所在と公開経路
- [ ] バックアップ・ダンプファイル(`*.sql`/`*.zip`/`.git/`)が公開ディレクトリに置かれていないか

## §10 個人情報・法令(日本)

- [ ] 取得する個人情報に利用目的の明示とプライバシーポリシーがあるか(個人情報保護法)
- [ ] **漏えい時の報告義務**への備え: 何が起きたら個人情報保護委員会への報告+本人通知が必要か(要配慮個人情報・1,000人分超・不正目的等)を運用者が把握しているか。連絡フローが文書化されているか
- [ ] 外部送信(解析タグ・広告タグ)の外部送信規律(電気通信事業法)対応: 送信先・内容の公表
- [ ] 越境移転: 個人データを国外のサービスに保存する場合の同意・公表
- [ ] 決済: カード情報を自社サーバーで**保持・通過させない**(トークン化決済か)。保持するならPCI DSS要件の確認
- [ ] 医療系: 患者情報・予約情報の扱いは要配慮個人情報として最上位の保護(アクセス制御・暗号化・ログ)

## 出力フォーマット

```
# セキュリティレビュー結果: (対象)(YYYY/MM/DD)
## 判定: 出荷可 / 条件付き出荷可 / 出荷不可

## 検出事項(深刻度順)
| # | 深刻度 | 箇所(file:line) | 分類(§) | 内容 | 修正案 |

深刻度基準:
- Critical: 認証なしでデータ漏えい・改ざん・実行に至る(§1漏えい済みシークレット、SQLi、IDOR等)→ 出荷不可
- High: 条件付きで重大被害(XSS、CSRF、権限昇格)→ 修正後に出荷
- Medium: 多層防御の欠落(ヘッダ不足、レート制限なし)→ 期限付きで対応
- Low/Info: 推奨事項

## 未確認事項
(スコープ外・環境にアクセスできず確認できなかった項目を正直に列挙)

## 再発防止
(lint/CIへの組み込み提案: 秘密検出のpre-commit、npm auditのCI化等)
```

## 原則

- チェックを通したふりをしない。確認できなかった項目は「未確認」と明記する(空欄の✓は監査の偽装)。
- 修正提案は具体的なコード・設定の差分レベルで書く。
- Critical検出時は他の作業より優先してユーザーに報告する。
- 本番環境・第三者のシステムに対する能動的な攻撃的検証(実際のペイロード送信)は、明示的な許可がある場合のみ。
