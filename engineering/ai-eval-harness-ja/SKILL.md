# 評価ハーネス構築スキル(ハーネスエンジニアリング)

AIの出力品質を**感覚でなく仕組みで**担保する。「評価ハーネス・自動採点・Human-in-the-Loop」の3層構造で、量の検証を機械に寄せ、人間は設計判断に集中させる。プロンプト側の設計は `engineering/prompt-engineering-ja`、PDCAへの接続は `management/pdca-runner-ja`。

## 1. 構築の4フェーズ(全体工数の目安: 1〜1.5ヶ月)

| フェーズ | 成果物 | 工数目安 |
|---|---|---|
| ① 評価セット設計 | 評価データ(JSON/CSV) | 3〜5人日 |
| ② 自動評価の実装 | 採点スクリプト+メトリクス | 5〜10人日 |
| ③ CI回帰検知 | CIワークフロー+ダッシュボード | 3〜5人日 |
| ④ 段階投入・継続評価 | シャドー/カナリア基盤 | 10〜15人日 |

小さく始めてよい(①だけでも「感覚評価」からは大きく前進する)。

### ① 評価セット設計
- 規模: **最低50件、理想200件**。構成比は **正常系50% / 境界ケース30% / 敵対的入力20%**
- 合格条件は完全一致でなく「ゆるい条件」で: `must_include`(含むべき要素)/ `must_not_include`(含んではいけない要素)のフラグ方式
- 実業務の入力から作る(作文した理想ケースだけにしない)

### ② 自動評価(3層ハイブリッド)
1. **ルールベース**: キーワード有無・引用IDの存在・JSON構造・文字数(速い・確実・タダ)
2. **LLM採点(LLM-as-a-Judge)**: 意味的な妥当性・文脈整合。**判定モデルは生成モデルと別系統**にし、月次で人手評価との一致率を測る
3. **人手スポットレビュー**: 差分サンプリングで最終検証

### ③ CI回帰検知
- プロンプト・モデル・検索設定の変更ごとに全評価セットを自動実行(検証が数時間→数分になる)
- ベースラインは週次更新、**劣化閾値3〜5%**で失敗扱い、失敗ケースをPR/変更記録に自動添付

### ④ 段階投入(いきなり全展開しない)
1. **シャドー**(1〜2週): 本番リクエストを複製して新版に流し、出力は捨てて採点だけする
2. **カナリア**(1〜2週): 1〜10%のユーザーにだけ展開して監視
3. **全展開**: 継続監視。低スコアのセッションを月次で評価セットへ還流

## 2. AI生成コードの自動レビュー設計

AIでコードが量産される環境では、人間の全件レビューは破綻する。採点を設計して機械に寄せる:

### 評価4分類と採点
| 分類 | 主な項目 |
|---|---|
| 機能正当性 | 仕様準拠、テスト網羅、エッジケース |
| 設計品質 | 責務分離、命名、複雑度 |
| セキュリティ | 入力検証、認可、秘密情報(`security-review-ja` の観点を採点項目化) |
| 運用性 | ログ、エラー処理、性能 |

- 各項目を **2点(合格)/1点(要改善)/0点(重大欠陥)** で採点
- LLM採点の安定化: 差分のみを渡す/JSON出力を強制/**同一対象を3回採点して中央値を採用**

### 3レーン運用
| スコア | レーン | 扱い |
|---|---|---|
| 1.6以上 | Green | 自動マージ候補(人間は抜き取り確認) |
| 1.2〜1.6 | Yellow | 人間レビュー必須 |
| 1.2未満 | Red | 自動差し戻し(AIに修正指示して再投入) |

- 0点(重大欠陥)が1件でもあればスコアに関わらずRed
- **ハーネス自体の品質管理**: 過去の人間レビュー結果50〜100件とハーネス判定の相関を四半期ごとに測定し、相関0.7以上を維持するようルーブリックを調整する(採点器が壊れていたら全部が壊れる)

## 3. 運用の原則

- 評価セットは資産。`docs/eval/` でバージョン管理し、本番の失敗事例を毎月追加する(評価セットが古い=守っているつもりで守っていない)
- しきい値・レーン基準は初期値であり、実績で調整する(pdca-runner-jaの信頼台帳と同じ思想: 実績データで自動化範囲を決める)
- ハーネスの判定を人間が常に上書きしている状態は、ハーネスかルールのどちらかが間違っているサイン。放置せず原因を直す
