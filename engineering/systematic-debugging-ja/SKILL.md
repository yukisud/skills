# 体系的デバッグスキル

高スターのデバッグ系スキル(superpowers等)の中核手法を踏襲した、推測修正を禁止するプロセス。**「多分これだろう」で直す試行を2回失敗したら、必ずこのプロセスに切り替える。**

## 鉄則

1. **エラーメッセージを最後まで読む**。スタックトレースの最初の1行と、自分のコードが登場する最初のフレームを特定してから動く。
2. **再現できないバグは直せない**。修正の前に再現手順の確立を最優先にする。
3. **1回に変えるのは1つ**。複数の変更を同時に入れると、直っても原因がわからず再発する。
4. **症状でなく根本原因を直す**。null チェックを足して黙らせる前に「なぜ null が来たか」を答える。
5. 調査で得た事実と推測を分けて記録する(「事実: レスポンスが空/推測: タイムアウト」)。

## プロセス(4フェーズ)

### Phase 1: 再現と観測
- 再現手順を最小のステップで確立(入力・環境・タイミング)。「たまに起きる」場合は発生条件の共通項(時間帯・データ量・特定ユーザー)を先に絞る
- 期待動作と実際の動作を1文ずつで言語化する(これが書けない=問題を理解していない)
- 変更履歴の確認: **いつまで動いていたか**。`git log`・デプロイ履歴・依存更新・外部APIの仕様変更。直近の変更が最有力容疑者
```bash
git log --oneline --since="2 weeks ago" -- <該当ファイル/ディレクトリ>
git bisect  # 動いていたコミットが特定できる場合の最強手段
```

### Phase 2: 最小化と切り分け
- 二分探索で範囲を絞る: 処理の中間にログ/アサートを置き、正常な側と異常な側に分ける。繰り返して異常の発生点を特定
- レイヤーの切り分け: データ(入力が壊れている)/ロジック(処理が誤り)/環境(設定・権限・バージョン差)のどこか。**「ローカルでは動く」は環境差分リストの作成から**(env変数・Node/PHPバージョン・タイムゾーン・ロケール)
- 最小再現コードを作る(フレームワークから切り離して10行で再現できれば原因は目前)

### Phase 3: 仮説と検証
- 仮説は「◯◯だから、△△すれば□□になるはず」の形式で書いてから検証する
- 検証は仮説を**否定できる**実験にする(直ったことの確認だけでなく、原因でないことの棄却)
- 3つ仮説を出して有力順に検証。1つ目に固執して同じ場所を掘り続けない
- 仮説が尽きたら観測に戻る(Phase 2)。**観測せずに仮説だけ増やさない**

### Phase 4: 修正と再発防止
- 根本原因を1文で説明できてから修正する(説明できない修正は偶然直っただけ)
- 修正前に**そのバグを検出するテストを書き、失敗することを確認**→修正→テストが通ることを確認(回帰テスト)
- 同型のバグが他にないか横展開検索(同じパターンをgrep)
- 記録: 原因・修正・検出方法を残す(`docs/postmortem/` または PR説明文)。同じ調査を二度しない

## 調査報告の様式

調査を依頼された場合(自分で直さない場合)の報告フォーマット:

```
## デバッグ報告: (症状の1行要約)
- 再現手順: (最小ステップ。再現率も: 常に/10回中3回)
- 根本原因: (1文で。特定に至った証拠)
- 影響範囲: (この原因で他に壊れるもの)
- 修正案: (差分レベル。複数案あるなら推奨を明示)
- 再発防止: (検出テスト・lint・監視の提案)
- 未解明: (残った疑問。なければ「なし」)
```

## 本番障害時の追加ルール(順序が命)

1. **影響範囲の把握と止血が原因調査より先**(ロールバック・機能フラグOFF・メンテ表示)
2. 調査用にログ・状態を保全してから復旧操作(復旧で証拠が消える)
3. 顧客影響がある場合は調査と並行して報告(`management/client-report-generator-ja` のトーンで事実+対応+見込み)
4. 復旧後にポストモーテム(責任追及でなく仕組みの改善。日本の組織では特に「犯人探し」化を明示的に禁止する)

## アンチパターン(検出したら自分を止める)

- エラーも読まずにAI/検索の提案コードを貼って試す
- 「とりあえず再起動・キャッシュクリア」を原因理解の代わりにする(復旧手段としては可、調査の終点にしない)
- try-catchで握りつぶして「直った」ことにする
- 2つ以上の変更をまとめて入れて祈る
- 再現しないまま「多分直りました」で完了報告する
