# 既存ツール解析・改修スキル

中身を知らないツールを受け取り、**理解→文書化→安全な変更**の順で扱う。新規開発は `engineering/tool-development-ja`、バグの原因調査は `engineering/systematic-debugging-ja` に委譲。

## Phase 1: 解析(変更依頼があってもまず読む)

### 1-1. 全体像の把握
```bash
find . -type f | sort                 # 構成(隠しファイル含む)
git log --oneline -20 2>/dev/null     # 履歴があれば直近の変更傾向
```
- エントリポイント(何がどう起動するか: 手動実行/トリガー/cron/Webhook)を特定
- データフローを追う: 入力(どこから)→処理→出力(どこへ)。**外部への送信先と認証情報の所在**は必ず洗い出す
- 依存関係: ライブラリ、外部API、スプレッドシート・DBの参照先。バージョン固定の有無

### 1-2. 出所不明コードの安全確認
第三者製・出所の曖昧なツールは、動かす前に `engineering/skill-vetting` の観点(不審な外部送信・難読化・認証情報の窃取パターン)を通す。**解析目的でもいきなり本番データ・本番認証情報で実行しない。**

### 1-3. 現状仕様の文書化(逆仕様書)
解析結果を必ず文書に残す(次に触る人=未来の自分への最大の貢献):

```
# 現状仕様: (ツール名)(解析日)
## 何をするツールか(1段落)
## 起動方法とトリガー
## データフロー(入力元→処理概要→出力先)
## 外部依存(API・認証情報の場所・ライブラリ)
## 把握できた暗黙のルール(マジックナンバー、ハードコードされた前提、手動運用とセットの箇所)
## 不明点(読んでも意図がわからない箇所。憶測で埋めず列挙)
## リスク(エラー処理なし、シークレット直書き、更新停止した依存 等)
```

## Phase 2: 変更・修正

### 2-1. 変更前のセーフティネット
- [ ] バックアップ/ブランチを切る(GASは版の複製、スプレッドシートはコピー作成)。**元に戻せる状態を作ってから触る**
- [ ] 現状の正常動作を1回実行して記録する(変更後の比較基準。既に壊れているものを「自分が壊した」ことにしない)
- [ ] 本番と切り離した検証環境(テストデータ・テスト用シート)を用意。無理なら影響範囲が最小の時間帯・データで

### 2-2. 変更の原則
- **1つの依頼=1つの変更系統**。修正とリファクタリングと機能追加を1コミットに混ぜない(壊れたときに戻せなくなる)
- 動いているコードの書き直し衝動を抑える。汚くても動いているコードには**そうなった理由(対応した実データの癖)が埋まっている**前提で、挙動を変えない範囲の整理に留める。全面書き直しはユーザーの明示的な合意を得てから
- 変更箇所の周辺だけ既存のコードスタイルに合わせる(自分の流儀への一斉変換をしない)
- 不明点リストに関わる箇所を変更する場合は、先に挙動を実験で確認してから(推測で「多分未使用」を削らない)

### 2-3. 検証と納品
- 変更対象の機能+**変更していない主要機能**の両方を動作確認(回帰確認)。2-1で記録した正常動作と突合
- セキュリティに触れる変更(認証・外部送信・権限)は `engineering/security-review-ja` を差分実行
- 変更記録を残す: 変更内容/理由/影響範囲/確認したこと。逆仕様書も更新する

## 完了報告の様式

```
## 改修報告: (ツール名)
- 依頼内容と対応結果(完了/一部/見送り)
- 変更点(ファイル・関数レベル)
- 動作確認の内容と結果(変更機能+回帰確認)
- 解析で見つけた別のリスク(依頼外だが報告すべきもの。勝手に直していない)
- 更新した文書(逆仕様書・README)
```

## 原則

- 「ついで」で依頼外の箇所を直さない。見つけた問題は報告に載せ、対応は別依頼として提案する。
- 解析で認証情報・個人情報を発見した場合は、内容を表示・転記せず所在と リスクだけ報告する。
- 挙動を完全に理解できていない箇所への変更は、その旨を明示してリスクをユーザーに判断してもらう(理解の偽装が最も危険)。
