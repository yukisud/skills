# 業務プロンプト設計スキル

「動くプロンプト」ではなく「業務に投入できるプロンプト」を設計する。検証は `engineering/ai-eval-harness-ja`、RAGの検索側は `engineering/rag-design-ja` と連携。

## 1. 基本構造(すべてのプロンプトの土台)

人間に仕事を頼むときと同じ情報を渡す:
1. **コンテキスト**: 依頼者の立場・状況・背景(「私は◯◯の担当で、△△のために使う」)
2. **タスク**: 何を・どの形式で(成果物の構成要素まで指定)
3. **読み手**: 誰が読むか・その人の知識レベル(「ITに詳しくない人でも分かるように」)
4. **トーン・制約**: 文体、避ける表現(「専門用語は使わない」「言い訳がましくしない」)
5. **例**: 期待する出力の見本(あれば精度が段違い)

- 曖昧な依頼(「いい感じに」)を受けたら、この5要素に翻訳してから実行する。1回で完璧を狙わず反復改善を前提にする
- 繰り返し使うプロンプトは**テンプレート化して変数部分を明示**し、プロンプト辞書(リポジトリの `prompts/` 等)に蓄積する

## 2. ハルシネーション防止の設計パターン10

業務システム(特にRAG・ナレッジ回答)に組み込むときの定番。組み合わせて使う:

| # | パターン | 書き方・実装 |
|---|---|---|
| 1 | コンテキスト限定 | 「提供されたコンテキストのみを根拠に回答する」と明示(学習データからの創作を遮断) |
| 2 | 引用ID要求 | 参照チャンクにIDを付与し、回答にsource_idsを必須化(根拠なし回答を後段で機械検知できる) |
| 3 | 出力スキーマ固定 | answer / confidence / source_ids 等のJSONスキーマを規定 |
| 4 | 「分からない」の許可 | 「該当情報がない場合はその旨を答えてよい」と明示(**答えない選択肢を与えるだけで業務ドメインの幻覚が3〜5割減る**) |
| 5 | 信頼度の自己申告 | confidence: high/medium/low を出力させ、low は人間確認に回す |
| 6 | 検証チェーン(CoVe) | 回答後に「事実主張をコンテキストで裏取りせよ」を実行(数値の捏造に効く) |
| 7 | 反例のFew-shot | 「答えない例」を回答例に混ぜて、抑制の行動を学習させる |
| 8 | 役割・範囲の明示 | 「◯◯の範囲のみを扱う」とスコープを限定(越境質問への捏造防止) |
| 9 | 数値の再計算強制 | 式を書かせてからコード実行で計算(暗算をさせない) |
| 10 | 出力前セルフチェック | 「回答がコンテキスト内に存在するか確認してから出力」を最終段に |

## 3. 業務投入前の検証手順(作って終わりにしない)

プロンプトは**テストしてから**業務に入れる。検証セットの規模基準:

| テスト区分 | 件数目安 | 内容 |
|---|---|---|
| 通常ケース | 50〜100件 | 想定される典型的な入力 |
| 境界ケース | 30件以上 | **コンテキストに答えが存在しない質問**(正しく「分からない」と言えるか) |
| 敵対的入力 | 30件以上 | 誘導・曖昧・矛盾する質問、インジェクション試行 |
| 長文ケース | 10件以上 | コンテキスト上限近くの入力 |

- プロンプトを改修したら**全件を再実行**(回帰テスト)。感覚で「良くなった」と判断しない
- この検証の自動化・CI化は `engineering/ai-eval-harness-ja` に委譲(幻覚率20%超→数%まで下げた実務例のあるプロセス)
- 検証セット自体を資産として `docs/eval/` に保存し、本番で見つかった失敗ケースを毎月追加する

## 4. アンチパターン

- 1つの巨大プロンプトに全業務を詰める(分割して連結する — `ai-agent-design-ja` §2)
- 「正確に答えて」「嘘をつかないで」だけ書く(具体的な機構=上記パターンがないと効かない)
- 検証なしの本番プロンプト差し替え(必ず回帰テストを通す)
- ユーザー入力とシステム指示を同じ文字列に混ぜる(タグで構造的に分離 — インジェクション対策は `rag-design-ja` §4)

## 出力様式

プロンプト設計の納品は「プロンプト本文+設計意図(採用したパターンと理由)+検証セットの雛形(区分別に最低10件)」の3点セット。
