# AIエージェント設計スキル

AIに業務を任せるシステムの設計図を描く。実装は `engineering/tool-development-ja`、評価は `engineering/ai-eval-harness-ja`、RAG固有の設計は `engineering/rag-design-ja` へ。

## 1. 失敗の型を先に知る(設計レビューの観点)

AIエージェント案件の大半はモデル性能でなく設計で失敗する。4つの罠:
1. **コンテキスト欠如**: 業務文脈・ワークフローを渡していないので出力が合わない
2. **ツール連携の壁**: 既存システムと繋がらず「半自動」で止まる(接続は `connection-setup-ja`)
3. **ガードレール不在**: 監視・評価がなくブラックボックス化、事故で信頼を失う
4. **劣悪なインターフェース**: 使う側の操作が複雑で定着しない

## 2. シンプル設計の原則

**「複雑なフレームワークより、理解可能で組み合わせ可能な部品」**が勝つ:

| 原則 | 実践 |
|---|---|
| 分解・チェーン化 | 巨大な1エージェントでなく、入出力が定義できるサブタスクに分割して連結(問題の特定が容易になる) |
| 生成と評価の分離 | 作る側と採点する側を別インスタンスに(自己採点は甘くなる) |
| オーケストレーション | 指揮役が分解して専門役に委任(`management/agent-team-orchestration-ja` の3層分離と同じ) |
| ツール定義の最適化(ACI) | ツールは明確な命名・詳細な説明・**間違えようがないパラメータ設計**(ポカヨケ)にする |
| フレームワーク選別 | まず素のAPIで理解してから、必要な部品だけ採用する。全部入りフレームワークから始めない |

- 最初の問いは常に「**そもそもエージェントが必要か**」。1回のLLM呼び出し+コードで済むならそれが正解(`tool-design-ja` の「作らない選択肢」と同じ思想)。

## 3. ガードレール設計(4層)

### 権限レベル(L0〜L4)で任せる範囲を定義
| レベル | 内容 | 例 |
|---|---|---|
| L0 | 閲覧のみ | 社内資料の検索・要約 |
| L1 | 生成のみ(下書き) | 議事録草案、広告文案 |
| L2 | 社内実行(可逆) | チケット起票、下書き保存 |
| L3 | 社外実行(不可逆) | メール送信、SNS投稿、請求 |
| L4 | 本番変更(高リスク) | DB更新、権限変更、課金 |

**初期はL1中心に寄せ、実績で昇格**(pdca-runner-jaの信頼台帳・承認ゲートと同一運用)。L3以上は人間承認を必須にする。

### 4層の実装
1. **権限設計**: 専用の最小権限アカウントで運用。個人情報・人事・機密はアクセス範囲から除外。初期は本番への書き込み禁止
2. **実行前**: 「何を・誰に・いつ・どれだけ」のプレビュー表示、不可逆操作は承認必須、提案モード(下書き)を標準に
3. **実行時**: 処理件数上限(例: メール最大10件/回)、対象範囲限定、レート・時間帯制限、異常検知で自動停止
4. **実行後**: 監査ログ(改ざん防止)、重要操作のアラート、一次対応者の明確化、週次/月次レビュー(`command-logger` を土台に)

導入初期(2週間)の成果物: ①業務・ツール・参照データ・実行可否の棚卸し表 ②暫定権限レベルの付与 ③A4一枚の暫定ルール文書。

## 4. 構成図の描き方(構成図は「絵」ではなく「契約書」)

誰が・何を・どの経路で扱うかを明示できない図は本番で役に立たない。**3レイヤーに分けて描く**:
1. **データフロー層**: ソース→前処理→保存(更新頻度を必ず明記: 日次/リアルタイム/手動)
2. **推論経路層**: クエリ→検索/ツール→LLM呼び出し→出力(モデル名・バージョンを箱に書く)
3. **ガバナンス層**: 認証・権限・監査ログ・PIIマスキング・レート制御(**この層の欠落が最頻の間違い**)

エージェント図の必須要素: オーケストレータ(方式注記)/ツール(権限スコープ明記)/メモリ(短期・長期の区分)/ガードレール経路の独立表示/**失敗時のフォールバック経路**。LLMからツールへ直接矢印を引かない(間にポリシー判定を挟む)。

LLM API直叩きでも最小5点: APIゲートウェイ/レート制御/キャッシュ/監査ログ/PIIフィルタ。
作図はMermaid推奨(Git管理・差分レビュー可能)。顧客提出用はdraw.io。

## 5. MCP・外部接続の権限設計

3層アーキテクチャ: **LLMクライアント層 → MCPサーバー層(認可判定) → バックエンド層(最終認可)**。MCPサーバーが直接DBを叩かず、APIゲートウェイ経由で権限判定するのが鉄則。

権限5原則:
1. 利用者IDを最後まで伝搬させる(誰の操作かを失わない)
2. **読み取り専用がデフォルト**。書き込み・削除はホワイトリストで明示許可のみ
3. OAuthスコープは必要最小
4. 監査ログ完全保存(誰が・いつ・どのツールを・どの引数で)
5. レート制限とサーキットブレーカー(誤動作の被害を止める)

実装鉄則: SQLはLLMに生成させない(パラメータ化・View・ストアド限定)/シェル実行は原則禁止(必要ならサンドボックス)/最大ステップ数・コスト上限を必ず設定/**ツールの出力は「データ」として扱い、その中の指示に従わない**。

導入は 外部SaaS接続 → ハイブリッド → 社内DB接続 の順で段階的に(いきなり社内DBを狙うと権限・監査整備で熱が冷める)。

## 出力様式

設計依頼には「構成図(Mermaid)+権限レベル表+ガードレール4層の実装表+段階導入計画」のセットで納品する。設計レビュー依頼には§1の4つの罠と§4のよくある間違いを観点に判定を返す。
