# LINE公式アカウント運用スキル

日本ではメールよりLINEが再来店・リピートの主力チャネル。獲得(広告・LP)からLINEに落とし、ブロックされずに再来を作る運用を設計する。メール側の設計は `marketing/hubspot-ops-ja`、獲得側は `creative/lp-builder-ja`(LP内の友だち追加CTA)と連動。

## 0. 料金プランと配信設計の前提

- 従量課金制(無料プランは月200通程度、上位プランで数千〜数万通。**最新の通数・料金は公式で確認**してから設計する)。
- 「配信通数=友だち数×配信回数」なので、友だちが増えるほど全体配信のコストが上がる。**初期からセグメント配信(絞り込み配信)前提で設計**し、全体一斉配信を既定にしない。

## 1. アカウント設計

### 友だち追加の導線(獲得)
| 導線 | 施策 |
|---|---|
| 店内・院内 | 会計時の声かけ+POP/カードのQR。**追加の場でその場で特典が使える設計**(「次回使える」より追加率が高い) |
| LP・サイト | 固定フッターに追加ボタン(`creative/lp-builder-ja`)。「LINEで気軽に相談」を電話・フォームと並ぶCVとして扱う |
| 広告 | LINE広告の友だち追加キャンペーン(CPF)。獲得単価と、その後の来店率をセットで評価 |

- 特典設計の注意: 医療は値引きを不特定多数へ誘引に使うと品位・規制リスク(過度な割引訴求は医療広告ガイドラインの品位保持に抵触しうる)。「相談しやすさ」「予約の便利さ」を主特典にする。

### あいさつメッセージ(追加直後・最重要)
1通目で (1)何が届くか (2)頻度 (3)何ができるか(予約・相談)を明示し、**期待値を設定してブロックを予防**する。長文にしない(3吹き出し以内)。

### リッチメニュー
- 常設の主要動線を6分割以内で: 予約 / サービス案内・料金 / アクセス / よくある質問 / 相談(チャット) / キャンペーン等
- **最頻の行動(予約)を最大面積・右下(親指位置)に**。デザインは `creative/design-review-ja` でレビュー。

## 2. 配信運用

- 頻度: 月2〜4回まで。それ以上はブロック率が跳ねる。**「配信することがないなら配信しない」**を許容する
- 時間帯: ターゲットの可処分時間(主婦層=平日昼、会社員=夜20〜21時等)。深夜配信はしない
- 1配信1メッセージ(訴求詰め合わせにしない)。冒頭1行目がプッシュ通知に出るため、そこで用件とベネフィットを言い切る
- セグメント例: 来店歴あり/なし、購入・利用メニュー別、最終来店からの経過日数
- コンテンツの型: 空き枠案内(直近キャンセル枠は反応が良い)/ 季節の啓発(検診月間)/ 新メニュー / よくある質問の解説。**売り込み:役立ち=1:2程度**の比率を守る

### ステップ配信(自動)
友だち追加からの自動シナリオ: 追加直後(あいさつ+特典)→3日後(選ばれる理由・実績などの信頼情報)→7日後(予約・購入への後押し)。未予約者のみに送る条件を付ける。

### リマインド(予約型ビジネスの最重要機能)
- 予約前日リマインド+前々日の変更受付導線で無断キャンセルを減らす(予約システムのLINE連携があれば自動化、なければ運用で)
- 再来サイクル(美容室なら1〜2ヶ月、定期検診なら3〜6ヶ月)に合わせた再来促進配信は、LINEの効果が最も出る施策。**最後に来た日ベースのセグメント**を作る

## 3. 法令・ポリシー

- [ ] 配信内容も広告規制の対象になりうる: 医療広告ガイドライン・景表法・ステマ規制のチェックは広告と同基準(`marketing/google-ads-ja-ops` §5)
- [ ] トーク(1:1チャット)で受けた症状相談・個人情報は要配慮個人情報に準じて扱う。対応者を限定し、スクリーンショットの社内共有ルールを決める
- [ ] 医療の場合、診断・治療判断に踏み込む返信をチャットでしない(対面への誘導までにする)
- [ ] 抽選・プレゼント企画は景表法の景品規制(総付・懸賞の上限)を確認

## 配信の実行(Messaging API)

配信文の納品で止めず、承認済みの配信を**実際に送信するまで**行う。承認キューは `marketing/sns-organic-ja` §3 と同方式(1配信1ファイル、status: draft→approved→sent)。

セットアップ(初回): LINE Developersでチャネル作成→チャネルアクセストークン(長期)を発行→環境変数 `LINE_CHANNEL_ACCESS_TOKEN` へ(.env管理・コミット禁止)。

```bash
# 全員配信(broadcast)
curl -X POST https://api.line.me/v2/bot/message/broadcast \
  -H "Authorization: Bearer ${LINE_CHANNEL_ACCESS_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"messages":[{"type":"text","text":"(承認済み本文)"}]}'
# セグメント配信(narrowcast)は audience 指定で同様。配信前に
# 対象者数を GET /v2/bot/insight/followers 等で確認し、従量課金の通数を概算してから実行
```

- **実行ゲート**: 配信は外部公開+従量課金なので、status: approved かつ概算通数の確認後にのみ実行。実行後はレスポンスの requestId と配信日時をファイルに追記(二重配信防止)
- 配信結果(開封・クリック)は翌週のPDCAサイクル(`docs/pdca/LINE運用.md`)で回収し、§4のKPI表に蓄積する

## 成果物の様式

- **設計依頼** → アカウント設計書(目的/導線別の獲得施策/あいさつメッセージ全文/リッチメニュー6枠の配置と遷移先/ステップ配信シナリオ)
- **配信作成依頼** → 配信文の完成形(吹き出し単位で区切る)+配信対象セグメント+配信日時案+§3の法令チェック結果
- **月次レビュー依頼** → 下記KPI表+翌月の配信カレンダー案(3〜4本)

## 4. KPIと月次レビュー

| 指標 | 見方 |
|---|---|
| 友だち追加数 / 導線別内訳 | どの導線が効いているか |
| ブロック率 | 累計30%前後は正常範囲。**配信直後のブロック急増はコンテンツ・頻度の警告** |
| 配信クリック率 | セグメント別に比較。全体配信との差でセグメントの価値を証明 |
| 予約・来店(LINE経由) | 最終KPI。リッチメニュー・配信・ステップ別に計測 |

月次で「配信内容×反応」の一覧を作り、勝ちパターンを`gtm/positioning-messaging-ja` のフレームワークに還元する。報告は `management/client-report-generator-ja` の様式で。
