# プロダクトディスカバリースキル

「作ってから外れる」を防ぐ、作る前の検証プロセス。テレサ・トーレス系の継続的ディスカバリー手法を日本の実務向けに軽量化したもの。顧客の生データ収集は `gtm/customer-research-ja`、検証後の文書化は `product/prd-ja`、事業数値との接続は `gtm/gtm-strategy-ja` のKPIツリー。

## 1. 機会の構造化(機会解決ツリー / OST)

アイデアから議論を始めない。**成果→機会→ソリューション→実験**の順にツリーを作る:

```
望む成果(例: 継続率をX%→Y%)
├─ 機会A(顧客の未解決の困りごと。顧客の言葉で書く)
│   ├─ ソリューション案1 ─ 実験
│   └─ ソリューション案2 ─ 実験
└─ 機会B ...
```

- 機会は**顧客インタビュー・問い合わせ・行動データから**書く(社内の思いつきは「仮説」ラベルを付けて区別)
- 1つの機会に必ず複数のソリューション案を出す(1案しかない=検討していない)
- 「その機能を作るべきか」と聞かれたら、まずどの成果・どの機会に紐づくかを問い、紐づかないなら作らない判断を提案する

## 2. 仮説の洗い出し(8カテゴリ)

ソリューション案ごとに、成立に必要な仮説を分解する:
1. **価値**: 顧客はこれを欲しがるか(最重要・最も外れる)
2. **ユーザビリティ**: 使い方が分かるか
3. **実現可能性**: 技術的に作れるか(`engineering/tool-design-ja` に照会)
4. **事業性**: 儲かるか・戦略に合うか(`gtm/pricing-strategy-ja` と接続)
5. **市場**: 十分な数の顧客がいるか
6. **チャネル**: 届けられるか(`gtm/gtm-strategy-ja` のチャネルマップ)
7. **法規制**: やってよいか(業種別の規制チェック)
8. **運用**: 回し続けられるか(サポート・保守の負荷)

## 3. 優先順位付け(Impact × Risk)

全部は検証できない。マトリクスで絞る:

- **Impact** = 検証で得られる価値 × 影響する顧客数(ICEなら Impact×Confidence×Ease、Opportunity Score = 重要度×(1−満足度) を使う)
- **Risk** = (1 − 確信度) × 外れたときの被害

| | Risk低 | Risk高 |
|---|---|---|
| **Impact高** | 検証せず実装へ進んでよい | **最優先で実験を設計**(ここが本命) |
| **Impact低** | 後回し | 案自体を棄却 |

順位付けの結果は表で出し、**「今週テストすべき仮説」を1つ**に絞る(`management/pdca-runner-ja` の1サイクル1変更と同じ)。

## 4. 実験の設計(意見でなく行動を測る)

各検証仮説に対して、最小の実験を設計する:
- **行動を測る**: 「使いたいですか?」アンケートは証拠にならない。事前登録・仮LP のCVR・有償プレオーダー・手動運用(コンシェルジュMVP)など、**顧客がコストを払う行動**で測る
- 実験の必須3点: 検証する仮説(1つ)/成功基準(数値としきい値を**実験前に**決める)/期限
- 実験の強度は仮説のリスクに合わせる(スモークテスト→プロトタイプ→限定リリースの段階)。最初から作り込まない
- 広告・LPを使う実験は `marketing/google-ads-ja-ops`・`creative/lp-builder-ja` で実行し、判定は `data-science/ab-test-analysis-ja` の統計基準で

## 5. 出力様式

```
## ディスカバリー報告: (テーマ)(日付)
### 機会解決ツリー(現状版)
### 仮説一覧と優先順位
| 仮説 | カテゴリ | Impact | Risk | 判定(実装へ/実験/後回し/棄却) |
### 今週の実験(1つ)
仮説 / 方法 / 成功基準(事前定義) / 期限 / 担当スキル
### 判明したこと(検証済みの学び。反証も含める)
```

継続運用時は `docs/discovery/<プロダクト名>.md` に累積し、検証済み/棄却済みの仮説を資産化する(同じ議論を二度しない)。
