# ロードマップ&OKR設計スキル

「機能の納期一覧」を「成果へのベット一覧」に変える。PRD(`product/prd-ja`)の上位文書であり、事業KPIツリー(`gtm/gtm-strategy-ja`)と接続する。

## 1. 成果ベースロードマップ(機能型からの変換)

機能一覧型(「Q1: 機能A、Q2: 機能B」)は、作った瞬間に約束になり検証を殺す。変換手順:

1. 既存ロードマップの各機能に「この機能で何の数値が動くはずか」を問う
2. 答えが同じ機能を**成果(Outcome)**の単位に束ねる(例: 「初回体験の完了率向上」)
3. 表現を変える: 「Now(確定・詳細)/ Next(方向確定・手段は柔軟)/ Later(仮説)」の3レーン
4. 各成果に測定指標と現状値を付ける。指標のない成果はロードマップに載せない

- 対外・経営向けに納期が必要な場合はNowレーンのみ日付を約束し、Next/Laterは四半期粒度に留める(全部に日付を入れると全部が遅延報告になる)
- 成果の中の具体手段の選定は `product/product-discovery-ja` で検証してから確定する

## 2. North Star Metric(NSM)と入力指標

- NSMの条件: **顧客が受け取った価値を表し**、かつ売上の先行指標であること(売上そのものはNSMにしない——遅行指標のため)。例: ゲームなら「週あたりコアループ完了ユーザー数」、予約型なら「月間実施予約数」
- NSMは1つ。分解した**入力指標3〜5個**(獲得・活性化・継続・単価など)をチームの持ち場に割り当てる
- 計測できないNSMを選ばない(`data-science/ga4-analysis-ja` で取れるかを設計時に確認)

## 3. OKR設計(日本の組織で機能させる)

```
Objective: 定性的で覚えられる方向(1〜3個。「〜な状態になっている」)
Key Results: 各O に2〜4個。現状値→目標値の数値(SMART)。施策名をKRにしない
```

運用の注意(日本の現場で死ぬパターンと対策):
- **KRがタスクリスト化する** → KRは「何が変わったか」、タスクは別管理(施策は変えてよい、KRは変えない)
- **人事評価と直結させて全員が安全な目標を出す** → OKRは評価と切り離すか、達成度でなく挑戦度・学習を評価する方針を先に明文化
- **期初に作って放置** → 週次でKRの現在値を見る場を固定(`management/pdca-runner-ja` の台帳にKRを載せると自動で回る)
- 上位OKRとの整合は「下から提案→上とすり合わせ」の往復で作る(トップダウン一方通行は形骸化する)

## 4. スプリント計画・振り返り(軽量版)

**計画**: キャパシティ(稼働可能時間×0.7)→ 優先ストーリーの選定(受け入れ基準があるものだけ)→ リスク・依存の確認。詰め込みは計画でなく願望
**振り返り(レトロ)**: 「続けること/やめること/試すこと」の3問+**前回の「試すこと」の実施確認**(やりっぱなし防止)。人でなく仕組みに原因を求める(`systematic-debugging-ja` のポストモーテムと同じ原則)

## 出力様式

```
## ロードマップ&OKR: (プロダクト名)(期)
### North Star Metric と入力指標(現状値付き)
### OKR
| O / KR | 現状 | 目標 | 計測方法 | 確認頻度 |
### ロードマップ(Now / Next / Later)
| レーン | 成果 | 指標(現状→目標) | 主な手段(仮説) | 検証状態 |
### 変換メモ(機能型から変換した場合: 落とした機能とその理由)
```

四半期の見直し時は、実績が入ったKPIツリー(`gtm-strategy-ja`)・PDCA台帳から逆算して更新する。
