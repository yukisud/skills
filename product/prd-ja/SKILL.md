# PRD作成スキル(日本の開発現場向け)

「何を作るべきか・なぜか」を定義する文書。**tool-design-ja(どう作るか=技術仕様)の1つ上流**に位置し、PRD→仕様書→実装の順で受け渡す。小さな社内ツールにPRDは過剰——機能が複数チーム・顧客に影響するときに使う。

## 8セクション構成

```
1. サマリ(2〜3文): この文書は何についてか。ここだけで回覧先の判断がつくこと
2. 関係者: 起案者・決裁者・開発・デザイン・関係部門(名前と役割。日本の現場では
   「誰が決裁者か」の明記が特に重要——曖昧だと後半で仕様がひっくり返る)
3. 背景: なぜ今か。何が変わったのか(市場・技術・自社の変化)。
   「前からやりたかった」は背景にならない
4. 目的とKey Results: 会社と顧客それぞれへのベネフィット、戦略との整合、
   成功の測定方法(SMART形式。「使いやすくする」でなく「◯◯完了率をX%→Y%」)
5. 対象セグメント: 誰のために作るか。デモグラでなく「抱えている課題・ジョブ」で
   定義する(gtm/positioning-messaging-ja のターゲット定義と同じ規律)
6. 価値提案: どのジョブ・ペインに応えるか、代替手段より何が良いか
7. ソリューション: 7.1 UX(ワイヤー・ユーザーフロー) / 7.2 主要機能 /
   7.3 技術(関係ある場合のみ。詳細は tool-design-ja の仕様書へ委譲)
8. リリース計画: フェーズ分け、スコープ外の明記(「やらないことリスト」が
   スコープクリープ防止の本体)、依存関係
```

- 書く前に4間: 何の問題を解くか/誰のためか/成功をどう測るか/制約と前提は何か。答えられないセクションは「未確定」と明記して仮説で書く(空欄より仮説+検証予定)
- 根拠データがあるもの(顧客の声・数値)は出典を添える。`gtm/customer-research-ja` / `product/product-discovery-ja` の出力が主なインプット

## ユーザーストーリーへの分解

開発に渡す粒度はストーリー形式で:
- **ユーザーストーリー**: 「(役割)として、(目的)のために、(機能)がほしい」+INVEST基準(独立/交渉可能/価値がある/見積可能/小さい/テスト可能)
- **ジョブストーリー**: 「(状況)のとき、(動機)したい、そうすれば(成果)」——文脈が重要な機能はこちらが向く
- 各ストーリーに**受け入れ基準**(Given/When/Then または箇条書きの完了条件)を必ず付ける。受け入れ基準のないストーリーを開発に渡さない(`tool-design-ja` の受け入れ条件と同じ思想)
- テスト観点(正常系・境界・エラー時)は `pm-execution` 的にはストーリーとセットで洗い出す。エッジケースの検討漏れが日本のQA工程で一番手戻りを生む

## レビュー観点(既存PRDのレビュー依頼時)

- [ ] 目的のKRが測定可能か(計測手段まで書いてあるか)
- [ ] 「やらないこと」が明記されているか
- [ ] セグメントがデモグラ定義になっていないか
- [ ] ソリューションが目的・価値提案と1対1で繋がっているか(目的にない機能が混ざっていないか)
- [ ] 決裁者が明記され、合意ゲート(`tool-design-ja` の4段ゲート)を通っているか
- [ ] 重要な仮説が検証済みか未検証か区別されているか(未検証なら `product-discovery-ja` へ)
- [ ] リリース前に `management/premortem-redteam-ja` を通したか

## 出力様式

新規作成は8セクションの完成ドラフト+未確定事項リスト(誰に何を確認すべきか)のセット。更新時は変更履歴(日付・変更点・理由)を文書末尾に残す。保存先は `docs/prd/<機能名>.md` を既定とする。
