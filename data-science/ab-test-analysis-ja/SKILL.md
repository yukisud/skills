# A/Bテスト分析スキル

「なんとなく勝ってそう」を禁止し、統計的な判定と業務判断を返す。LP・広告・SNS・プロダクトのあらゆるテスト判定の共通基盤(lp-builder / ad-creative / product-discovery の実験はすべてここで判定する)。データが渡されたらPythonで計算し、計算過程を残す。

## 1. 実験セットアップの検証(数字を見る前に)

結果より先に、テスト自体が壊れていないかを確認する:

- [ ] **仮説と主要指標が事前に決まっていたか**(結果を見てから指標を選ぶのは統計的に無効=当たりが出るまでサイコロを振る行為)
- [ ] **サンプルサイズ**: 期待する効果量(MDE)に対して十分か。n = (Z²α/2 × 2 × p × (1−p)) / MDE² で概算し、検出力80%未満なら「アンダーパワー」と明記
- [ ] **期間**: 最低1〜2営業サイクル(週次変動をまたぐ)。開始直後の新規性効果(物珍しさで一時的に上がる)が抜けているか
- [ ] **SRM(サンプル比率の不一致)**: 50/50設計なのに47/53のような偏りがないか(カイ二乗検定。SRMがあれば配信システムの不具合で、**結果全体が無効**)
- [ ] 期間中の外部イベント(セール・テレビ露出・障害)の混入

## 2. 統計計算(渡されたデータで実行)

1. 各群のCV率と**相対リフト**((施策群−対照群)/対照群)
2. **p値**(2群の比率の両側z検定 or カイ二乗検定)と**95%信頼区間**
3. 判定: 統計的有意(p<0.05)かつ**実務的有意**(そのリフト幅がビジネスとして意味があるか——0.1%改善が有意でも実装コストに見合わないことがある)

## 3. ガードレール指標の確認

主要指標の勝ちだけで判定しない。悪化していないかを併せて確認:
- 収益・客単価 / 解約・離脱 / 表示速度 / 問い合わせ・クレーム数
- **主要指標が勝ってもガードレールが壊れていたら「勝ち」ではない**(例: CVRは上がったが単価の低い客層ばかり増えた)

## 4. 判定と推奨(意思決定に翻訳する)

| 結果 | 推奨 |
|---|---|
| 有意な改善+ガードレール正常 | **採用**(全展開。展開後1週間は監視) |
| 有意な改善+ガードレール懸念 | **調査**(トレードオフを理解してから判断) |
| 有意でない+改善傾向 | **延長**(必要サンプルまでの残日数を計算して提示) |
| 有意でない+差なし | **中止**(意味のある差はない。次の仮説へ) |
| 有意な悪化 | **不採用**(対照群に戻す。なぜ外れたかを学びとして記録) |

- 少トラフィックで有意に届かない場合の代替案を提示する: MDEを大きく取る(大胆な変更をテストする)/中間指標(FV直帰率等)で判断/定性調査に切り替え——**「n不足のまま僅差で判定」だけはしない**
- 多変量・多重比較(3案以上)の場合は検定の多重性を補正(Bonferroni等)するか、上位2案の再テストを推奨

## 5. コホート分析(継続率系の判定)

継続・リピートが指標の場合は時点比較でなくコホートで見る:
- 獲得週/月ごとのコホート×経過期間のリテンション表を作る
- 施策の影響は「施策後に獲得したコホートのカーブ」と「施策前コホートの同経過時点」の比較で判定(全体平均は新規流入の増減で歪む)
