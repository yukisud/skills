# データ突合QAスキル

レポートに載せる数値の正しさを、独立した経路で取得したデータと突合して保証する。クライアント報告(`client-report-generator-ja`)の前工程として使う。

## 突合の基本原則

1. **同じ経路を2回見ない**: ダッシュボードの数値はその元クエリで検算しても意味がない。管理画面 vs API、API vs エクスポートCSV のように独立経路で照合する。
2. **完全一致を求めすぎない**: 経路間の許容誤差を事前に決める(目安: 広告指標±1%、GA4系±5%。サンプリング・集計遅延があるため)。許容内は「一致」と扱い、超過のみ調査する。
3. **不一致は定義ズレをまず疑う**: バグより先に指標定義・期間・タイムゾーン・フィルタの差を確認する。

## 頻出の不一致原因チェックリスト(日本環境)

### 期間・時刻
- [ ] タイムゾーン: 広告アカウントがAsia/Tokyo設定か。APIのdate指定とダッシュボードの期間が同じTZか
- [ ] 集計確定の遅延: Google広告のCV数は計測後も数日さかのぼって更新される(コンバージョン列 vs 「コンバージョン(推定)」)。**直近3日を含む期間の突合はズレて当然**
- [ ] 比較期間の日数違い(前月比で30日vs31日)

### 指標定義
- [ ] 「コンバージョン」の中身: 全CVアクションか、主要CVのみか(Google広告の「コンバージョン」列は入札対象CVのみ)
- [ ] クリックとセッションを混同していないか(クリック≠GA4セッション。10〜30%ズレるのが正常)
- [ ] 費用: 税抜/税込、手数料込みか(日本の代理店手数料20%込み表示のズレは頻出)
- [ ] 平均値の計算: 「CPAの平均」を単純平均していないか(必ず合計費用÷合計CVで再計算)
- [ ] 率の再集計: CTR・CVRを期間合算する際に日次の率を平均していないか

### 接続・欠損
- [ ] Looker Studioのコネクタ更新失敗・キャッシュ(データの鮮度表示を確認)
- [ ] ブレンドデータの結合キー欠落(日付形式の不一致、キャンペーン名の変更で結合漏れ)
- [ ] フィルタ・セグメントの残留(除外フィルタがかかったまま)

## 実行手順

1. **対象の定義**: 突合する指標・期間・粒度(日次/月次/キャンペーン別)を列挙し、経路A(レポート側)と経路B(生データ側)を決める。
2. **データ取得**: 両経路から同一条件で取得。CSVがあれば計算で再現する(合計・率の再計算はスクリプト化して `scripts/` に残す)。
3. **突合表の作成**:

```
| 指標 | 粒度 | 経路A | 経路B | 差分 | 差分率 | 判定(許容内/要調査) |
```

4. **要調査項目の深掘り**: 上のチェックリスト順に切り分ける。粒度を細かくして(月→日→キャンペーン)ズレの発生箇所を特定する。
5. **是正と再発防止**: 原因が定義ズレなら、レポート側に**指標定義の注記**を追加する(直すだけでなく、次回また混乱しないように)。

## 出力フォーマット

```
## 検証結果: 合格 / 要修正

## 突合表
(上記の表)

## 検出した不一致と原因
| 指標 | 差分 | 原因 | 是正内容 | 再発防止 |

## 検証条件
(期間、TZ、許容誤差、データ取得日時 — CV遅延の注意含む)
```

## 運用ルール

- クライアント報告書の数値は、初回構築時と**レポート定義を変更した月**に必ずフル突合する。定常月は主要3指標(CV・費用・CPA)のみのライト突合でよい。
- 突合結果は `docs/data-qa/` に日付付きで保存し、「この定義ズレは既知」のナレッジを蓄積する。
- 不一致の原因が特定できないまま報告書を出さない。間に合わない場合は該当数値に「速報値」と注記する。
