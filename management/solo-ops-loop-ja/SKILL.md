# 個人・小規模事業のAI運営ループ

AIを「コードを書く道具」でなく「事業を24時間動かす社員」として使う運営モデル。核は**秘密のプロンプトではなく「顧客の問題→修正→測定」のループを極端に短縮し、浮いた時間をマーケに回すこと**。個別作業は既存スキルへ委譲し、このスキルは全体の回し方を持つ。

## 大原則

- **AIは供給を生むが需要は生まない。** 需要確認なしの大量開発を禁じる。作る前に「払う顧客がいるか」(`product/product-discovery-ja` の行動を測る実験)を通す
- 開発と販売は**50:50**。機能を増やすより、既存機能を売る時間を確保する
- 技術構成は「自分とAIが全体を把握できる範囲」に留める(`engineering/tool-design-ja` の作らない選択肢・最小構成)。理解できない複雑さは事故と停滞を生む

## 1. 日次ループ(これを毎日回す)

```
朝: メトリクス確認(売上・登録・解約・エラー)→ 異常があればそれが今日の1問
午前: 最も価値の高い問題を1件だけ選ぶ(全部やろうとしない)
昼: AIに「完了条件」で指示(§3)→ ステージングで実装・テスト
午後: 人間が本番反映を承認 → 公開 → 顧客へ通知
夜: 今日の失敗を CLAUDE.md のルールに変える(§2)
```

- メトリクス確認は `data-science/ga4-analysis-ja` / `sc-ga4-report-ja`、収益系は接続済みなら自動レポート化(`management/pdca-runner-ja` の定期起動に載せる)
- 「今日の1問」は複数施策を並行しない(pdca-runnerの1サイクル1変更と同じ)

## 2. CLAUDE.md を業務マニュアルとして育てる

プロジェクト直下の `CLAUDE.md` を、AIに毎回渡す常設の業務マニュアルにする。含める要素:
- **プロダクトの目的と技術構成**(何のための何か、どのファイル・サービスで動くか)
- **建築方針と禁止事項**(使う技術/使わない技術、触ってはいけない箇所)
- **ワークフローと安全性ルール**(ステージング必須、本番反映は人間承認、ロールバック手順)
- **完了条件の定義**(何をもって「完了」とするか)

運用: **失敗するたびにルールを1行足す**(同じ失敗を二度させない)。CLAUDE.mdは書いて終わりでなく、日次ループの夜フェーズで育て続ける資産。設定・hooksの整備が必要なら `update-config`、監査ログは `management/command-logger`。

## 3. 完了条件型の指示(「コードを書いて」と言わない)

AIには作業でなく**到達すべき状態**を渡す(`engineering/tool-development-ja`・`agent-team-orchestration-ja` の受け入れ条件と同じ):
```
- 目的: (なぜやるか)
- 現状: (今どうなっているか)
- 変更範囲: (触ってよい場所/ファイル)
- 完了条件: (複数。この操作をしてこうなったら完了、を検証可能に)
- 禁止事項: (触ってはいけないもの・やってはいけないこと)
- 作業後の報告: (結論/変更点/確認したこと/懸念)
```

## 4. 段階的権限とセーフティ(コードレビューより優先するもの)

個人運営では全コードを精読できない前提で、**仕組みで守る**:
- **Planモード/調査は権限制限**、実装・テストは**ステージング環境**、本番反映のみ人間が最終判断(`engineering/ai-agent-design-ja` の権限L0-L4、`pdca-runner-ja` の承認ゲート)
- レビューより **自動テスト・本番前動作確認・エラー監視・数分で戻せるロールバック** を優先(`engineering/tool-development-ja` の出荷ゲート)
- 本番での権限確認スキップは**隔離環境に限る**。本番でそれをやらない

## 5. 常時稼働とバックグラウンド処理(任意)

- ローカルPCでなくVPS等の常設環境+永続セッション(tmux等)にすると、閉じても動き続けデプロイも速い。プロダクトごとにディレクトリ・セッションを分け「その部屋に入る」だけで再開できる
- 非対話実行(バックグラウンド)で夜間に調査・修正案を用意させ、朝に人間が承認する運用も可能。ただし**外部公開・課金・不可逆操作は必ず承認ゲートを挟む**(自走の範囲は§4の権限設計に従う)
- 運営業務(売上レポート・問い合わせ分類・返金処理・不正検知)のうち定型化できるものはスクリプト化(`engineering/tool-development-ja`)し、pdca-runnerの定期実行に載せる

## 6. 需要優先の30日ローンチ

新規プロダクトはこの順で(供給から作らない):
1. **1週目**: 販売ページで需要検証(払う顧客がいるか。`creative/lp-builder-ja` + `product/product-discovery-ja`)
2. **2週目**: 中心機能だけ実装(アクセス解析・課金・エラー監視は最初から入れる)
3. **3週目**: 運営基盤整備(CLAUDE.md、環境隔離、自動テスト)
4. **4週目**: 毎日1改善→顧客へ通知(開発と販売を50:50に)

## 出力様式

- 立ち上げ相談 → 30日ロードマップ(週次ゲート付き)+ CLAUDE.md雛形 + 需要検証の実験設計
- 運用相談 → 日次ループの現状診断(どのフェーズが回っていないか)+ 自動化候補リスト(効果×工数)
- 常に「今日の1問」に絞る。やることを増やす提案でなく、減らして回す提案をする
