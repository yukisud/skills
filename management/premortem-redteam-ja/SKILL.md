# プレモーテム&レッドチームスキル

丁寧なフィードバックしか受けていない計画を、本番の前に攻撃する。対象はPRD・GTM計画・キャンペーン・値上げ・組織変更など**計画全般**。2つのモードを持つ(依頼に応じて選択、迷ったら両方):

- **プレモーテム** = 「失敗した未来」から逆算してリスクを洗い出す(網羅型)
- **レッドチーム** = 計画を支える前提そのものを攻撃する(急所特定型)

## モード1: プレモーテム

1. **失敗を宣言する**: 「リリース/開始から2週間後、この計画は失敗した。顧客は使わず、数字は未達で、信頼を落とした」と仮定して、何が起きたかを列挙する
2. **リスクを3分類する**:
   - **虎(Tiger)**: 根拠・経験・論理から実在すると考える本物の脅威。対処必須
   - **張り子の虎(Paper Tiger)**: 誰かが心配しているが、実際は起きにくい・影響が小さいもの。**文書化して関係者と目線を合わせる**(議論の蒸し返し防止)のが目的で、リソースは割かない
   - **象(Elephant)**: 誰も口に出していないが検証もされていない不安。会議で言いにくい類のもの(「そもそも需要あるのか」等)。調査対象に昇格させる
3. **虎を緊急度で分ける**: リリースブロッカー(解決するまで出さない)/ 30日以内対応 / 監視のみ
4. **ブロッカー全件に対応計画**: リスクの記述/緩和策/担当/期限。担当と期限のない対策は対策ではない

## モード2: レッドチーム(前提への攻撃)

プレモーテムがリスクの網羅なら、こちらは**急所の特定**。長いリスクリストより、テスト付きの本物のキル前提5個の方が価値がある:

1. **主張を抽出する**: 計画が「真」として置いている前提を全部書き出す(顧客について・市場について・仕組みについて・時間軸について)。**外れたら計画が死ぬ前提(急所)**だけを攻撃対象にする
2. **スチールマンしてから攻撃する**: 各前提について「なぜ正しいと言えるか」の最強版をまず書き、**その最強版を**攻撃する(弱い解釈を叩いても無意味)
3. **失敗条件を「◯◯なら失敗する」形式で書く**: 具体的・反証可能に(「実行リスク」ではなく「活性化がボトルネックでなければ失敗する」)
4. **(外れたときの影響)×(外れている確率)×(検証の安さ)でランク付け**し、上位3〜5個に絞る
5. 各キル前提に**実行者がすぐ動ける3点**を付ける:
   - 今週取りに行く証拠(具体的なデータ・クエリ・会話)
   - 撤退基準(この閾値を割ったら止める/方向転換する)
   - 最安のテスト(信念を動かす最小の実験 → `product/product-discovery-ja` の実験設計へ)
6. **疑いを捏造しない**: 根拠のしっかりした前提は「よく立証されている」と明言する。難癖製造機になったレッドチームはゴム印と同じくらい無価値

## 出力様式

```
## プレモーテム/レッドチーム: (計画を1行で)
### キル前提ランキング(3〜5個)
- 前提: / ◯◯なら失敗する: / 今週取る証拠: / 撤退基準: / 最安のテスト:
### リスク分類(プレモーテム実施時)
| 分類(虎/張り子/象) | 内容 | 緊急度 | 対応(担当・期限) |
### よく立証されている点(疑いを捏造しない)
### 判断材料不足で評価できなかった点
```

## 運用ルール

- 実施タイミング: PRD確定前・GTM Phase移行前・大きな予算投下前・値上げ通知前。`pdca-runner-ja` の承認ゲート対象(公開・予算増額)は原則このスキルを通してから承認依頼を出す
- 計画の作者と攻撃者は別セッション/別エージェントで(`agent-team-orchestration-ja` の生成・評価分離)
- 結果はお蔵入りさせず、キル前提の検証をPDCA台帳のPに接続する(攻撃して終わりはただの評論)
