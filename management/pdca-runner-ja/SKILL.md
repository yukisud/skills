# PDCA運転スキル

**完了の定義は「提案」ではなく「実行と記録」。** すべての実働スキルの出力をこの台帳に接続し、サイクルとして回す。提案で止まってよいのは承認ゲート対象(下記)だけで、その場合も「承認依頼を出した」状態までがこのスキルの仕事。

## 1. 台帳(施策ごとに1ファイル)

`docs/pdca/<施策名>.md`:

```markdown
# PDCA台帳: (施策名)
- 目的とKPI: (例: 除外KW運用で無駄費用を月3万円削減)
- 判定データソース: (検索語句レポート/GA4/SC/OpenSEO — 取得手段まで)
- 承認ルール: (何は自動実行してよく、何は承認が要るか。初期値は§3)
- 撤退基準: (これを下回ったら施策自体を止める条件)

## サイクルログ(上が最新)
| # | 日付 | P: 仮説と変更内容 | D: 実行したこと(手段・対象) | C: 結果(数値・判定日) | A: 次の一手 |
```

- **1サイクル1変更**(複数同時に変えると効果が切り分けられない。systematic-debugging と同じ原則)
- **判定基準は実行前に書く**(P欄に「◯◯がX%改善したら成功」まで書いてから実行。後出しの成功判定を禁止)
- C欄が空のまま次のPを書かない(検証をサボったサイクルは回っていない)

## 2. 1サイクルの運転手順(定期起動時はこの順で)

```
1. 台帳を読む(前回のA=今回のP)
2. C: 前回変更の結果データを取得して判定
   (ga4-analysis / sc-ga4-report / openseo / 検索語句レポート / SNS投稿台帳)
3. A→P: 判定に基づく次の変更を1つ決める
4. 承認判定(§3): 自動実行可 → 実行 / 承認要 → 承認依頼を作成して停止
5. D: 実行(各実働スキルの実行手段で)。実行できた事実(登録件数・投稿ID等)を確認
6. 台帳更新+実行ログ(何をいつ変えたか。巻き戻し方法も1行)
7. 異常検知(KPI急落・撤退基準接触)があれば通常サイクルを止めてユーザーへ即報告
```

## 3. 承認ゲートの初期ルール

| 自動実行してよい(実行→事後報告) | 承認必須(依頼を出して停止) |
|---|---|
| 除外KWの追加(共有リスト) | 予算の増額・入札戦略の変更 |
| 承認済みキューのSNS/LINE配信実行 | 新規の対外的な文言・クリエイティブの初回公開 |
| レポート・台帳・分析の生成 | 価格・オファーの変更 |
| 記事の下書き作成(非公開) | 記事・LPの公開、広告の配信開始/停止 |
| データ取得・監視 | 不可逆な削除、金銭が発生する契約・課金 |

- このルールは `agent-team-orchestration-ja` の**信頼台帳**で運用実績に応じて緩和する(20回×成功率95%で左列へ昇格)。緩和の判断は必ず人間が行う
- 実行手段が未接続の施策は、**入稿可能な完成物+実行手順**の納品を「D」とみなし、台帳に「未接続(手動実行待ち)」と明記する。接続レジストリ(§4)に追加要望を残す

## 4. 接続レジストリ(何が実行でき、何が納品止まりか)

`docs/connections.md` に接続状態を一元管理し、各サイクルの冒頭で参照する:

```markdown
| 接続先 | 状態 | 実行できること | 認証の所在 |
| X API | 接続済 | 投稿(post_to_x.py) | .env |
| HubSpot | 未接続 | (接続後: コンタクト・取引の読み書き) | — |
| Google Ads API | 未接続 | (接続後: 除外KW登録・レポート取得) | — |
```

新しい接続ができたら該当スキルの「接続あり」の実行経路が有効になる。接続作業は `engineering/connection-setup-ja`(サービス別ランブック)が担当し、開発を伴う連携は `engineering/tool-development-ja` へ。

## 5. 自動運転の設定(サイクルを人が起動しない)

- 週次施策: 定期実行(Claude Codeのスケジュール実行・cron・CIのschedule)で「`docs/pdca/` の全台帳について pdca-runner-ja の手順2〜7を実行」というプロンプトのセッションを起動する
- 定期起動時の出力は3行サマリ(施策別: 実行したこと/結果/承認待ちの有無)+台帳更新。**変化がなければ黙って台帳だけ更新**し、承認待ちと異常だけ通知する
- 監査: 実行系の操作は `management/command-logger` のログに残る前提で運用する

## 原則

- 「検討します」「推奨します」を D 欄に書かない。D は実行した事実だけ(実行できなければ理由と承認依頼)
- サイクルが3回連続で改善ゼロなら、変更の粒度を疑う(小さすぎ)か施策の筋を疑う(撤退基準の見直しをユーザーに提起)
- 台帳は施策の記憶そのもの。セッションが変わっても台帳から再開できる書き方をする(文脈を知らない人が読んで次が打てるか)
